# План розвитку Constella: Premium і AI

## Продуктова мета

Перетворити Premium із набору механічних переваг на відчутну допомогу в знайомствах: швидше починати розмову, краще розуміти спільність і безпечніше переходити від матчу до зустрічі. AI запускаємо як реальну функцію продукту, а не лише обіцянку на лендингу.

## Що вже є в коді

- VIP-підписка за Telegram Stars (499 Stars / 30 днів) та entitlement-модель із планами `vip`, `plus`, `prime`.
- Серверна перевірка активного Premium уже є (`hasVip`); основний UX і логіка підписок існують у web та mobile.
- Профілі мають інтереси, матчі та чат; WebSocket-відлуння й tRPC уже працюють на обох клієнтах.
- Є окремий `ai/nsfw` сервіс для модерації зображень. На момент формування roadmap генерації тексту ще не було; для неї додано окремий `ai/assistant`, типізований API-клієнт і внутрішній токен, без узагальненого AI gateway.

## Продуктове рішення для першого релізу

**Premium AI Chat Coach** — доступний активним `vip` / `plus` / `prime` без окремої оплати за кожен запит. У першій версії AI пропонує до трьох коротких варіантів наступного повідомлення на основі вибраної теми розмови та спільних інтересів. Користувач редагує або відкидає підказку; AI ніколи не надсилає її сам.

V1 не передає моделі історію чату. Це дає корисний старт із меншим ризиком для приватності. Аналіз недавніх повідомлень — окремий наступний етап: лише після зрозумілого opt-in, повідомлення користувачу про обробку, визначеного строку зберігання провайдера й перевірки політики приватності.

Поточні плани `vip`, `plus`, `prime` проходять одну й ту саму перевірку `hasVip`; не додаємо ще один тариф і не змінюємо ціну 499 Stars заради першого тесту. Ліміти використання потрібні для захисту витрат і сервісу, а не як прихований продаж кредитів.

## Архітектура Premium AI

```text
Web / Mobile chat
  -> authenticated tRPC assistant.suggest
      -> API: active entitlement + match membership + quota + input validation
          -> typed assistant client (internal token, timeout)
              -> ai/assistant service -> approved text model provider
```

API є єдиним місцем авторизації Premium: клієнтський прапорець лише показує/ховає кнопку й не є контролем доступу. Провайдер моделі не отримує доступу до Postgres, R2 чи Telegram credentials. Для MVP вибрати провайдера лише за наявності умов «не використовувати дані для тренування» та прийнятного retention; якщо такі умови не підтверджені — не надсилати приватний контент і не запускати аналіз історії чату. Модель/провайдера можна змінювати за адаптером сервісу, але не будувати окрему універсальну платформу.

## Приватність, якість і зловживання

- У першому релізі не передавати повідомлення співрозмовника, адресу, телефон, точні координати, вік як чутливий сигнал чи інші дані, не потрібні для формулювання репліки.
- Явно маркувати AI-підказки; не видавати їх за гарантовано успішний флірт, психологічний висновок чи факт про іншу людину.
- Обробляти текст профілю/теми як недовірений ввід, а не інструкції моделі; обмежити формат і довжину відповіді, фільтрувати небезпечний або образливий результат.
- Не навчати модель на чатах Constella. Зберігати лише агреговану телеметрію без текстового вмісту; передбачити видалення/відключення AI-функції.
- Перевірити доступ при завершеній/скасованій підписці, неактивному чи чужому матчі, заблокованих користувачах, спробі зловживання квотою та недоступному AI сервісі.

## Метрики та рішення про масштабування

Зняти базову лінію до запуску й аналізувати окремо Premium-когорту: частка тих, хто скористався AI; частка підказок, вставлених у чернетку; частка фактично відправлених повідомлень після вставки; повторне використання за 7 днів; зміна кількості розмов, що отримали відповідь; оцінка корисності; latency, помилки й собівартість на активного Premium-користувача. Не трактувати частку відправлених AI-підказок як мету сама по собі — важливіше покращення якісного діалогу та утримання без зростання скарг/блокувань.

Масштабувати після пілоту, якщо вартість на Premium-користувача вкладається в затверджений бюджет, сервіс укладається в цільову затримку, а сигнали скарг/блокувань не погіршуються. За перевищення витрат — знизити квоту або вимкнути сервіс env-прапорцем, не змінюючи чат і платіжний контур.

## Порядок робіт для першого релізу

1. Зафіксувати UX, квоту, провайдера з прийнятними privacy-умовами та бюджетний cap.
2. Реалізувати сервіс, typed client, tRPC authorization/quota та unit-тести API.
3. Додати web і mobile composer UI та локалізацію; перевірити premium/free/expired сценарії на обох клієнтах.
4. Провести privacy/security review, перевірити відмову сервісу й kill switch, протестувати навантаження/вартість.
5. Увімкнути обмежений Premium-пілот; лише після метрик і перевірки trust/safety — масштабувати та оновлювати публічні обіцянки Premium.

## Свідомо не входить у v1

Автоматична відправка повідомлень, автономний AI-чат від імені користувача, оцінювання особистості/«сумісності» на основі приватних повідомлень, безконтрольна передача повної історії діалогу, навчання на переписках і нова AI-підписка поверх чинного Premium.

## Реалізаційний handoff

Оновлено: Premium AI Chat Coach MVP реалізований у коді, але **не запущений**. Перший етап завершено без увімкнення зовнішньої генерації чи застосування міграції до спільної БД.

### Статус roadmap

- Етапи 1–3 (AI service/API, web/mobile UX, kill switch і денна квота): реалізація в коді завершена й локальні build/tests пройшли; для локального inference додано Ollama у compose, приватний Docker network endpoint і persistent volume для моделі. Сервіс не розгорнутий, `AI_ASSISTANT_ENABLED` лишається вимкненим, міграція `0018` не застосована. Отже функція **не доступна користувачам і не готова до пілоту**. Потрібні перевірка ресурсів AI-box, завантаження моделі, deployment та перевірене застосування міграцій.
- Етап 4 (персоналізація): API, web і mobile мають структурований добровільний feedback із фіксованих причин. Поданий профіль виключається з повторного показу до кінця локального дня; фідбек не змінює довгостроковий ranking. UI не пропонує feedback для VIP-фільтрованих результатів, бо API приймає його лише для профілів добової орбіти. Web/mobile показують лише фактичні спільні інтереси. Premium AI profile coach ще не реалізований: не надсилати приватне біо/prompt провайдеру, доки не затверджено його retention/no-training. Повернутися до цієї функції після підтвердження приватності або за наявності локальної моделі.
- Етап 5 (safety): локальна реалізація приватного плану, share sheet, історії власних скарг і opt-in mobile-нагадування завершена; потрібні застосування міграцій `0019` і `0021`, а також перевірка UX на реальному мобільному пристрої.
- Загальний roadmap **не завершений**. Не запускати production/pilot й не вважати цю роботу повністю готовою, доки не закриті перелічені пункти та зовнішні умови.

### Реалізовано

- `apps/api/src/assistant/router.ts`: `assistant.status` повідомляє клієнтам про kill switch; `assistant.suggest` — захищений tRPC endpoint, який перевіряє `AI_ASSISTANT_ENABLED`, активний `hasVip`, існування матчу, участь користувача й блокування через `getMatchForUser`.
- `apps/api/src/assistant/client.ts`: типізований запит із внутрішнім токеном, таймаутом і валідацією рівно трьох відповідей. Модель отримує тільки `{locale, topic}`; `matchId` не передається.
- `apps/api/src/assistant/router.ts`: щоденний ліміт 10 на UTC-день резервується всередині транзакції з advisory lock, щоб паралельні запити не обходили обмеження. У `events` записуються лише ID користувача, тип події й дата; генераційний текст не зберігається. Невдала інференція теж витрачає спробу для захисту витрат.
- `packages/db/drizzle/0018_assistant_usage_index.sql`: індекс для запиту квоти; доданий у `_journal.json` і Drizzle-схему. **Міграцію не запускати автоматично** — вона потребує звичного перевіреного застосування до БД.
- `ai/assistant/`: окремий FastAPI сервіс із внутрішньою авторизацією, input/body limits, одним слотом, таймаутом провайдера, обмеженням/валідацією відповіді та privacy-safe логами. Підтримує OpenAI-compatible chat completions через операторську конфігурацію.
- `ai/nsfw/docker-compose.yml` і `Caddyfile`: окремий opt-in профіль `assistant` і проксі лише `/v1/suggest`; звичайний NSFW деплой не вмикає новий сервіс.
- `ai/nsfw/docker-compose.yml`: додано Ollama в той самий opt-in профіль, без публікації порту, з volume для ваг, healthcheck, одним паралельним запитом та конфігурованим 4K context. Покрокове завантаження `qwen3:8b` описане в `ai/assistant/README.md`; Docker у середовищі розробки відсутній, тому compose deployment не запускався.
- `apps/web/components/dashboard/ChatPanel.vue`, `apps/mobile/src/app/(app)/chat/[matchId].tsx`: Premium-CTA, введення теми, вибір із трьох варіантів і вставлення тільки в чернетку, без автоматичного надсилання. Додано локалізацію uk/en/de/fr та коротке пояснення про приватність.
- Тести: `apps/api/src/assistant/client.test.ts`, `apps/api/src/assistant/router.test.ts` (обидва додані в API test glob) і `ai/assistant/tests/test_generator.py`.

### Safety та рекомендації — поточний етап

- `apps/api/src/safety-plans/router.ts`: власник матчу може зберегти/прочитати/видалити лише свій план; перевіряється членство в незаблокованому матчі. Зберігаються дата, назва публічного місця й місто, без точних координат/контактів. `apps/web/components/dashboard/ChatPanel.vue` і `apps/mobile/src/app/(app)/chat/[matchId].tsx` мають форму та явно ініційований share sheet; одержувача обирає сама людина.
- Mobile може за окремим opt-in запланувати локальне сповіщення за годину до зустрічі; без дозволу або якщо до зустрічі менше години — план зберігається, але клієнт показує причину відсутності нагадування. Сповіщення містить тільки нейтральний текст і matchId для навігації, без місця/міста. Web чесно вказує, що reminder наразі доступний лише в mobile.
- `apps/api/src/recommendations/router.ts`: приймає тільки фіксований набір причин для профілю з поточної локальної орбіти. Таблиця має по одному запису на пару профілів/день, без довільних текстових деталей. Mobile Orbit дозволяє подати фідбек «Це не моє».
- Web і mobile Orbit мають однаковий фідбек UI; після подання картка зникає до наступного локального дня. Відфільтровані VIP-кандидати не показують контрол фідбеку.
- Публічний профіль містить лише конкретний перетин інтересів viewer/candidate для пояснення рекомендації; web/mobile показують його без AI-висновків про сумісність.
- Міграції `0019_private_meeting_plans` і `0020_recommendation_feedback` додані до Drizzle schema/journal, **але не застосовані**.
- `social.myReports` повертає тільки статус і дати скарг поточного користувача (без даних про ціль скарги або модераторських нотаток); останні 20 записів показуються у профілі web/mobile. `0021_reporter_history_index` оптимізує цей запит і очікує стандартного deployment.
- Додані schema tests `apps/api/src/safety-plans/schema.test.ts` і `apps/api/src/recommendations/router.test.ts`; обидва входять до API test suite.

### Умови перед пілотом

1. Безпечний шлях за замовчуванням для першого пілоту — приватний локальний inference endpoint на AI-box; не надсилати дані віддаленому провайдеру без окремого погодження no-training і retention. Модель та endpoint на AI-box ще потрібно provision-ити й перевірити.
2. На AI-box налаштувати `.env` за `ai/nsfw/.env.example`, підняти opt-in профіль за інструкціями `ai/assistant/README.md` і перевірити `/healthz`.
3. У стандартному deployment-контурі перевірено застосувати очікувані міграції `0018_assistant_usage_index`–`0021_reporter_history_index`; не запускати їх із локального середовища на спільній БД.
4. В API deployment задати `AI_ASSISTANT_URL`, той самий `AI_ASSISTANT_INTERNAL_TOKEN` (≥32 символів) і `AI_ASSISTANT_ENABLED=true`. Kill switch — unset/false `AI_ASSISTANT_ENABLED`.
